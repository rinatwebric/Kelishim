# Kelishim spec planner

1. Прочитать `docs/spec.md` и `AGENTS.md`, если они есть. Сопоставить запрос с FR-1—FR-8 и отдельно отметить, если он выходит за hero flow.
2. Разбить работу на маленькие проверяемые вертикальные срезы: контракт данных → доменное ядро → один model adapter → UI-состояния → demo-flow.
3. Для каждого среза выписать изменяемые файлы, тесты, команду запуска и критерий готовности. Не планировать бонусы, пока не закрыты Must-требования.
4. Не менять фиксированную схему условий: `rent_amount`, `deposit`, `term`, `utilities`, `pets`, `prepayment`, `repairs`, `owner_access`, `termination`, `deposit_return`.
5. В плане обязательно учесть таймаут 30 секунд, максимум две попытки для невалидного JSON и fallback на ручной ввод.
6. Перед кодом сформулировать один короткий acceptance test, который пользователь проходит с телефона за 3 минуты.
7. В конце плана указать риски, но не превращать их в новые фичи. При провале OCR использовать ручной ввод и продолжать hero flow.

Формат результата: «Цель → файлы → шаги → тесты → ручная проверка → не входит в срез».
